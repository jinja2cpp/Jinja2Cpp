# Load drift after trains 11 and 12

**Problem.** Master's Load instruction counts rose 0.7-3.8% between 84a70a4 and f11b3d2
(plain_text +3.8%, inheritance +3.1%, many_tags +2.1%), Render flat. The perf track's
bisection put all of train 11's step on #528 (0168 entry bindings; #526, 0169, counts the
same as its base) and the rest on #531 (0193 unknown filters and tests as load errors).
The 0168 task file estimated +1.7%; inheritance was +2.4% from it alone.

**What the profiles showed** (callgrind on Release builds with `-g`, per function and per
inlined source file, 84a70a4 against master):

- Fixed costs on every Load: `NameResolver::EntryBinding` and `Resolve` were called out of
  line for their early returns (about 50 Ir on plain_text, whose template has no tag);
  `TakeBody` grew past GCC's inlining limit, so every statement's body paid a call; the
  root `StatementInfo` was built and then moved into the stack.
- Per stored name: each `set`, macro, import or `with` target copied its name into a
  `std::string` twice (a temporary, then the `Store`), with the store list growing by 1.5x.
- Per name read: `m_reads` (inline room for 16) reallocated on any template with more reads,
  by 1.5x, through malloc.
- Per include or import with context: a `std::vector` allocation for the context read.
- Per expression: `UnknownCallables::Mark` divided the list's byte size by `sizeof(Name)`,
  twice per expression and twice per tag.
- Per frame that stores a name: `EntryBinding` hashed, sorted and matched every store against
  every read even where no read inside a nested frame could precede it.

**Done.** All of these are gone; the behaviour is unchanged (unit tests and the parity corpus
pass as on master):

- `EntryBinding`, `Resolve` and the new `MayBindAtEntry` check inline; `TakeBody` is
  always inlined and calls the out-of-line `TakeFrameBody` only for a frame that may bind.
- The resolver keeps stored names as views of arena text: set and `with` targets already
  were, the import namespace and aliases are now made in the arena before they are stored,
  and a macro's name too (a `MacroStatement` constructor takes the arena text).
- `m_reads` holds 64 reads inline and doubles; the store list doubles; context reads are a
  small_vector.
- `UnknownCallables` keeps its count.
- `MakeEntryBinding` first checks that some candidate store comes after the first read of
  the first nested frame: frames are numbered as they start, so any read inside comes after
  that one. Most frames fail the check and skip the hashing.
- `StatementInfo::OwnsFrame` is one mask test.

**Accepted cost.** What is left, +0.05..+1.35% against 84a70a4, is the bookkeeping the two
features need, spread thin with no single item above about 0.3%:

- 0168 records every name read (about 11 Ir each: the resolver must know which reads come
  before which store, in which frame), every stored name, whether each statement is in a
  branch (`SetInBranch`), and per frame its first read and store; a frame that does store a
  name read inside it still pays for the hashing and matching.
- 0193 marks the unknown-name list around each expression and tag, and each expression
  parser holds one more reference.
- Both add containers to the parser, which every Load constructs and destroys (about 25 Ir:
  most of plain_text's +26).

The rest is GCC moving code between inlined and out-of-line copies (`~StatementInfo` and
`Load` shift by a few Ir each way). Ways to go further, none worth its code today: record reads
only for names some frame stores, which needs the stores first (a second pass); or build the
resolver's lists in the template's arena.
